# Taste Learnings
- Prefers a plan-first workflow: present a detailed plan for review, wait for approval, then implement in one pass. Do not start creating files until the plan is approved. Confidence: 0.9
- Wants explicit stop-and-wait gates between phases (e.g. scaffolding → stop → get approval → implement logic → stop → get approval). Do not proceed to the next phase without explicit go-ahead. Confidence: 0.9
- Insists that all reference/context files (e.g. AGENTS.md, CLAUDE.md, rubric specs) are read fully before doing any work. Confidence: 0.85
- Prefers scaffolding and architecture before business logic: folder structure, schemas, config files, and stubs first; scoring/fetching/LLM logic only after the scaffold is reviewed and approved. Confidence: 0.85
- When implementing a batch of work within a phase, prefers file-by-file implementation with a review gate after each file, rather than all files at once. Order matters when files build on each other. Confidence: 0.85
- Enforces strict layered architecture: generic/cache layers must have zero domain knowledge; raw clients have zero caching logic; a wrapping client is the only public interface. Confidence: 0.85
- Tests must mock at the HTTP transport layer (respx/responses), never mock the project's own methods. No live API calls in tests. Confidence: 0.85
- Runs ruff + pytest after every single file change, not just at the end of a phase. Confidence: 0.85
- Wants retry-with-backoff on 429/5xx errors in HTTP API clients. Confidence: 0.8
- Prefers configurable parameters over hardcoded magic numbers — e.g. TTL should be a per-call override, not a single global constant, so future callers can tune behavior without modifying the class. Confidence: 0.85
- Insists that defensive/unreachable code branches have a one-line comment explaining why they exist and why they're not covered by tests, so they don't read as untested bugs to future readers. Confidence: 0.85
- Wants intentional design trade-offs (e.g. skipping expired cache rows instead of deleting them) explicitly documented in docstrings/comments, not left for readers to infer. Confidence: 0.8
- No live API calls at any point — always use recorded fixtures/responses; never call real external APIs, even outside of tests. Confidence: 0.85
- Prefers filtering/cleaning functions to return metadata about what was removed (e.g. filtered_out_count), not just the cleaned result, for transparency in downstream output. Confidence: 0.8
- Tests should assert on the actual correct answer derived from real data, even when that answer is an edge case (e.g. zero valid results) — explicitly note such cases as findings rather than bending the test to pass or fabricating expected values. Confidence: 0.8
